Where the visual direction is argued

Every mock here replaces floating cards — translucent fill, blur, box-inside-box — with flat panels and hairline dividers. That is a deliberate change and the Why flat tab makes the case, including what it costs. The short version: the app already set all five shadow tokens to none, so it stopped floating some time ago; what remains is translucency over an opaque black page (which computes to a flat colour) and a backdrop blur with nothing behind it to sample. The proposal finishes a decision that was already taken, rather than starting a new one.

Design principles the proposal holds to

  • One level of elevation per card.A panel is a surface with dividers inside it, not three nested bordered boxes.
  • Green means "live value or primary action".Never decoration. Today it is also used for borders, dots, eyebrows and hover text.
  • Numbers are the interface.Tabular figures, consistent decimal handling, unit always adjacent and always muted.
  • Motion confirms, it does not announce.Opacity and small scale only; nothing that reflows layout.
  • The public site and the app are the same product.Same header, same card, same button, same type scale — only the density changes.

Scope guardrails

  • No new dependencies. Everything below is achievable with the existing Tailwind v4 @theme block plus the components already in components/ui.
  • No routing or data-layer changes, except the two shell fixes flagged as bugs.
  • Existing tests reference Button, IconButtonGroup, StatusBadge, Icons and FormStyles — those get extended, not replaced.
  • tailwind.config.js is inert (v4 project, empty extend). Delete it so it stops implying a second source of truth.

Why the proposal drops floating cards

Every mock in this document replaces the floating-card pattern — translucent fill, blur, shadow, rounded box inside rounded box — with flat panels divided by hairlines. That is a real change in visual language, so here is the argument for it, in the order the evidence actually lands.

Short version: the app is not currently rendering floating cards. It is rendering the leftovers of them. The shadows were already removed; the translucency and blur that made the shadows read were left behind, and now cost paint without producing an effect.

The argument, condensed

  1. It is not a new direction — it is finishing an existing one. Setting all five shadow tokens to none already chose flat. The translucency, blur and nesting are residue from before that decision.
  2. The removed effects were not rendering. Alpha over an opaque page is a solid colour; blur over an opaque backdrop returns the backdrop. Both still cost a compositing layer per card.
  3. Shadow is unavailable on this palette. Nothing is darker than #000000, so depth has to come from lighter fill and hairlines. That is what a flat panel system is.
  4. It removes the cause of the token sprawl, not just the symptom. Twenty surface alphas exist because alpha was the only way to get an unnamed shade. Naming four opaque steps closes the loop.
  5. It buys content width where the product is used most — a phone, one-handed, mid-meal.
  6. It matches the installed form factor, which is where a daily-log app actually lives.

What this is not, and what it costs

  • Not "flat design" as a style. Depth is still expressed — through fill steps and lines rather than through simulated elevation. The hierarchy gets stronger, not weaker, because the four steps mean something.
  • Not the removal of all blur. The modal backdrop and the mobile nav sheet keep it: there is genuinely content behind them, so it does the job it is for.
  • Not the removal of radius. Panels stay at 16px. Rounding is shape, not elevation.
  • Real cost: fewer visual handholds. With no borders around sub-sections, spacing and typography have to carry the grouping. That is why the type scale and the 8px rhythm are prerequisites (phase 1.1/1.4), not optional polish — flattening without them would read as undifferentiated.
  • Real cost: a divider is weaker at a glance than a box. Where a section is genuinely a separate object — an upgrade prompt, a destructive action — it should still step a surface level rather than rely on a hairline. The mocks do this in every panel footer.
  • Real risk: it is a visible change. Anyone used to the current look will read the first build as "unfinished" for a day. Worth landing tokens and panels together rather than page by page.

Primitives — buttons, cards, inputs, tabs

These are shared, so every inconsistency here multiplies across all 21 pages. The pattern throughout is a reasonable primitive that call sites then override with a bespoke class string.

Problems

  1. highVariants that aren't distinct. secondary, neutral and outline are three greys with near-identical hover states. success is defined as a button but is only ever used to render status.Button.tsx lines 33–69.
  2. highSizes that can't be used as-is. BUTTON_SIZES.sm is px-2.5 py-1.5 text-xs. Every real call site adds min-h-11 — Navbar.tsx, Header.tsx, AuthPageShell.tsx, the blog filter chips, the calculator links.
  3. highgetButtonClasses() is being used to defeat itself. Hero passes "px-8 py-3.5 text-base font-semibold rounded-full", Header passes "rounded-full px-3 text-xs ... sm:px-4 sm:text-sm". The size argument is then meaningless.
  4. highThree-deep card nesting with no colour step. DailySummaryPanel.tsx renders CardContainer → CardContainer bg-surface-2 → 3× CardContainer bg-surface-2. Levels 2 and 3 are the same fill, so the nesting reads as clutter.
  5. lowThree focus treatments. Buttons use ring-2 + ring-offset-2, form inputs use outline-2 outline-offset-0 (FormStyles.ts), and global.css sets a third for everything else.
  6. lowDead markup in MetricCard. {score !== undefined && <div className="... mb-2 flex ..." />} renders an empty element whose only effect is 8px of margin.

  1. Five button variants. primary · secondary · ghost · danger · link. Fold outline into secondary, delete neutral, move success to StatusBadge.Button.test.tsx asserts on data-variant, so the removals need a test update, not a rewrite.
  2. Height in the size token. sm/md/lg all ≥44px; xs is the documented dense exception. Then delete every min-h-11 in the app.
  3. Make overrides visible. Keep className for layout only (w-full, margins). Anything touching padding, radius or font size becomes a size/variant prop.
  4. One card, one border. <Panel> with <Panel.Section> — sections are separated by hairlines, and only genuinely interactive rows step a surface level.
  5. One --ring token applied in global.css, removed from Button, FormStyles, TabButton and the ~40 inline focus-visible: chains.
  6. Delete the empty score div and either render the score or drop the prop.

Delivery context — browser tab vs installed

With no APK shipped, the two real delivery contexts are a Chrome/Safari mobile tab and the installed PWA. They behave differently enough that the bottom-bar and docked-action patterns proposed in the mobile tabs need explicit handling for each. This section is what changes between them.

What will actually break in a browser tab

  1. bugThe keyboard covers any fixed bottom element. index.html has no interactive-widget value, so Chrome Android uses resizes-visual and the layout viewport does not shrink. The Log sheet's confirm button and Settings' docked save would both end up behind the keyboard.
  2. bugOffline reload fails on every route except /. _redirects gives an SPA fallback at the host, which needs the network. The worker calls precacheAndRoute with no NavigationRoute / navigateFallback, so it only matches precached URLs. Workbox's default directoryIndex: "index.html" means a cold launch at start_url: "/" does work offline — but a refresh on /home or /goals does not.
  3. highenv(safe-area-inset-bottom) is frequently 0 in a tab, because the browser toolbar already occupies that region. Padding that relies on the inset alone collapses to nothing.
  4. highSafari iOS stacks its own bottom address bar under ours — about 110px of an 844px screen spent on chrome before any content.
  5. lowChrome Android's collapsing omnibox resizes the viewport on scroll, so anything sized in dvh reflows mid-scroll. Anchor to bottom: 0 rather than computing from viewport height.
  6. lowNo install prompt exists. No beforeinstallprompt handler anywhere, and no display-mode media query in the codebase — so there is currently no way for the app to know, or tell the user, that installing is an option.

What makes both contexts work

  1. Viewport meta becomes: width=device-width, initial-scale=1, viewport-fit=cover, interactive-widget=resizes-content. The first half turns on safe areas; the second half keeps docked actions above the keyboard. Both are needed before any bottom-anchored pattern here is safe to ship.
  2. Pad with max(env(safe-area-inset-bottom), 8px), never the raw inset — correct in standalone, correct in a tab, correct on a device with no home indicator.
  3. Add navigateFallback to the service worker so an offline refresh on any route serves the cached shell. One NavigationRoute + createHandlerBoundToURL("/index.html"); it also needs workbox-routing, which is not yet a dependency.
  4. Ship the bottom bar in both contexts. Two navigation patterns is a real maintenance cost, and the double-bar on Safari is cramped rather than broken. Use @media (display-mode: standalone) only to adjust padding — not to change the layout.
  5. Add an install prompt. With no APK, this is distribution. Capture beforeinstallprompt on Android for a real Install button; on iOS, where that event does not exist, show a "Share → Add to Home Screen" hint when display-mode: browser. Dismissible, and never shown again once installed.
  6. Self-hosting Inter also simplifies the CSP. _headers currently allows fonts.googleapis.com in style-src and fonts.gstatic.com in font-src; both can be dropped once the font is served from 'self'.

Worth knowing, given there is no APK

  • An installed PWA on Android is genuinely close to native here: own launcher icon, own entry in the app switcher, no browser chrome, real safe-area insets. A Play Store TWA is a separate step you do not need for any of this.
  • Installability looks satisfied already: HTTPS, a manifest with name, short_name, start_url, display: standalone and 192/512 icons, and a service worker with a fetch handler (precacheAndRoute registers one). The icon fixes in 4.3 improve quality, not eligibility.
  • iOS is the weaker target — no beforeinstallprompt, and storage for an installed PWA can be evicted after extended non-use. Worth knowing before treating iOS PWA as equivalent to Android.
  • Web push is not in play. The notification system in components/notifications is in-app toasts only, with no PushManager anywhere — so the usual iOS push caveats do not apply to this app.

Deliberately not proposed

  • A component library. The primitives here are fine; the problem is that call sites bypass them.
  • A light theme. color-scheme: dark is a product decision, not an accident.
  • Replacing motion/react. 45 files import it; the fix is using less of it, not swapping it.
  • Restructuring routes or features. The features/* layout is coherent. Only MainLayout's route sets change, and only because they're wrong.
  • Rewriting the Remotion hero. Proposal is to stop leading with it, not to remove it — it can move below the fold.
